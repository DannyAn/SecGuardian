# SecGuardian 重大架构重构指南 v2

\> **文档性质**: 架构重构执行指南，供 AI Agent 按步骤执行

\> **触发事件**: 2026-07-07 dogfood 会话 ses_0c39，MiniMax-M2.7 扫描生产仓库 idm（642 文件、3076 函数），检出 0 个漏洞，安全评分 100/100

\> **核心结论**: 系统在真实生产代码上完全失效——不是"检出少"，而是"完全扫不出问题"

\> **v2 变更**: 融合 ZhuqueLingMa（灵码）架构洞察，从"修补索引器"升级为"架构范式迁移"

## 0. 诊断：为什么扫不出问题？

### 0.1 会话回放：ses_0c39 的 7 分钟灾难

| 步骤 | 发生了什么 | 应该发生什么 |

|------|-----------|-------------|

| Step 1 | `.scan_state` 路径错误，`source` 失败，`SECGUARDIAN_HOME` 丢失 | 跨 shell 状态传递应可靠 |

### 0.2 根因分析：5 层致命缺陷

```

┌─────────────────────────────────────────────────────────┐

│  致命缺陷 #1: 索引器产出与检测器消费完全脱节              │

│  索引器记录"函数定义"（idm_access_token_init）            │

│  检测器需要"函数调用"（strcpy_s(dst, sizeof(dst), src)）  │

│  → 预筛逻辑永远匹配不上 → 检测器被全部跳过               │

├─────────────────────────────────────────────────────────┤

│  致命缺陷 #2: 调用图几乎为空（5 edges / 3076 functions）  │

│  文本匹配 callee_name( → 只匹配用户自定义函数间的调用     │

│  无法追踪 用户输入 → 危险函数 的数据流                    │

│  → 注入类检测器完全失效                                   │

│  规则排除 strcpy_s( → 永远不会触发 → 检测器空转           │

│  → securec.h 代码库（华为产品标配）100% 免疫检测          │

├─────────────────────────────────────────────────────────┤

│  致命缺陷 #4: LLM 作为检测引擎能力不足                    │

│  642 文件 × 67 检测器 = 43,000+ 组合需要验证              │

│  LLM 上下文窗口有限，无法系统性遍历                       │

│  LLM 倾向于"找不到就宣布安全"（确认偏差）                 │

│  → 0 检出不是"代码安全"，是"检测失效"                    │

├─────────────────────────────────────────────────────────┤

│  致命缺陷 #5: 无反馈回路，无法调优                        │

│  检出 0 个 → 无法区分"真安全"和"检测盲区"                │

│  没有已知漏洞的基准测试集（idm 不是故意含漏洞的示例）      │

│  无法微调单条规则的灵敏度                                 │

└─────────────────────────────────────────────────────────┘

```

### 0.3 与灵码（LingMa）的架构差距

灵码已在生产环境验证有效。对比两者的核心差异：

| 方面 | 灵码（已验证） | SecGuardian（失效） | 差距本质 |

|------|--------------|-------------------|---------|

| 检测执行 | Worker Agent 读实际代码 | LLM 读 index + grep | **Worker 看代码 vs LLM 看索引** |

| 规则结构 | SKILL.md + references/（4-6 文件） | 单个 guard-rule .md | **自包含协议 vs 扁平描述** |

| 安全变体 | 显式审计 `_s` 参数正确性 | 完全排除 `_s` | **审计 vs 忽略** |

| 证据链 | Source→Propagate→Sink 三段式 | 无结构化证据链 | **有链 vs 无链** |

| 精度控制 | suppress-first + 5 轮反思 | 无显式精度策略 | **防误报 vs 无策略** |

| 跨函数 | 深度限制 3，显式协议 | 无协议，依赖 call_graph（5 edges） | **有界搜索 vs 盲搜** |

| Skill 数量 | 30（专注 C/C++） | 67（跨 5 语言） | **聚焦 vs 分散** |

| 索引器 | 无（Worker 直接读代码） | 有但产出不可用 | **无索引 vs 有索引不可用** |

**关键洞察**: 灵码没有索引器也能检测，因为 Worker 直接读代码。SecGuardian 有索引器但产出不可用，反而成了绊脚石。重构的核心不是"修好索引器就够了"，而是**改变检测执行范式**。

## 1. 战略愿景：Dispatcher-Worker-Skill + 索引器信号聚焦

### 1.1 核心思路

```

灵码的胜利 = Dispatcher 编排 + Worker 读代码 + Skill 定义规则

SecGuardian 的潜力 = 索引器预扫描 + 信号聚焦 + Worker 精准读代码

融合方案 = 灵码的检测范式 + SecGuardian 的索引器优势

```

**不是修索引器让 LLM 能用，而是修索引器让 Worker 知道去哪找。**

### 1.3 与灵码的关键区别

| 方面 | 灵码 | SecGuardian v2 |

|------|------|---------------|

| Worker 输入 | 无预扫描，Worker 全量遍历 | **索引器产出 call_sites → Worker 只看相关代码** |

| Worker 调度 | Dispatcher 按 Skill 逐个调度 | **Dispatcher 按 call_sites 信号批量调度** |

| 跨函数追踪 | Worker 自行 grep 追踪 | **索引器提供调用图 → Worker 限定搜索范围** |

| 效率 | Worker 可能重复读同一文件 | **索引器去重 → 每个 Worker 只读必要文件** |

**核心优势**: 索引器不是替代 Worker，而是让 Worker 的搜索从"全量盲搜"变成"信号聚焦精准搜"。

## 2. 重构方案：4 个 Epic

### EPIC-1: 索引器重构 — 从"符号表"到"调用点信号图"

**当前问题**: `symbols.functions` 只记录函数定义，不记录函数体内的库函数调用。检测器预筛在符号表中查找 `strcpy` → 永远找不到。

**重构目标**: 索引器产出 `call_sites`（库函数调用点 + 参数摘要），作为 Worker 的任务清单。

#### 2.1.1 新增 `CallSite` 数据结构

在 `internal/parser/types.go` 中新增：

```go

type CallSite struct {

CallerFunction string   `json:"caller"`

CalleeName     string   `json:"callee"`

File           string   `json:"file"`

Line           uint     `json:"line"`

Arguments      []string `json:"arguments"`

IsSafeVariant  bool     `json:"safe_variant"`

Category       string   `json:"category"`       // "memory", "string", "io", "crypto", "exec", "sync"

}

```

在 `ParseResult` 中新增：

```go

type ParseResult struct {

File      string         `json:"file"`

Language  string         `json:"language"`

Functions []FunctionInfo `json:"functions"`

Variables []VariableInfo `json:"variables"`

Types     []TypeInfo     `json:"types"`

CallSites []CallSite     `json:"call_sites"`

}

```

#### 2.1.2 Tree-sitter 解析器提取调用点

在 `parser_ts.go` 的 walk 逻辑中，对每个 `function_definition` 节点的 body，遍历 `call_expression` 子节点：

```

function_definition

└── body (compound_statement)

└── call_expression          ← 提取此节点

├── function             ← callee 名称

└── argument_list        ← 参数摘要

```

**nil 守卫**: 每个 `node.Child(i)` 后必须 nil 检查（沿用 AGENTS.md 约定）。

对 C/C++ 重点提取以下库函数调用：

| 类别 | 函数名 | 安全变体 | category |

|------|--------|---------|----------|

| 字符串操作 | strcpy, strcat, sprintf, gets | strcpy_s, strcat_s, sprintf_s, gets_s | string |

| 内存操作 | memcpy, memmove | memcpy_s, memmove_s | memory |

| 内存分配 | malloc, calloc, realloc, free | — | memory |

| 文件操作 | fopen, fclose, open, close, tmpfile | fopen_s, freopen_s | io |

| 命令执行 | system, popen, exec* | — | exec |

| 环境变量 | getenv | — | exec |

| 线程同步 | pthread_mutex_lock, pthread_mutex_unlock | — | sync |

| 加密 | AES_*, RSA_*, DES_* | — | crypto |

**关键**: `IsSafeVariant` 标识 `_s` 安全变体。Worker 对安全变体**不跳过**，而是审计参数正确性。

#### 2.1.3 正则回退解析器提取调用点

在 `parser_re.go` 中，用正则模式提取调用点：

```go

var callSitePatterns = []struct {

{"calloc", `\bcalloc\s*\(`, false, "memory"},

```

#### 2.1.4 调用图重构为基于 `call_sites`

```go

func BuildCallGraphV2(callSites []CallSite, symbols SymbolIndex) CallGraph {

cg := CallGraph{}

for _, cs := range callSites {

cg.Edges = append(cg.Edges, CallGraphEdge{

Caller: cs.CallerFunction,

Callee: cs.CalleeName,

File:   cs.File,

Line:   cs.Line,

})

}

return cg

}

```

不再限制只匹配用户函数间的调用。库函数调用也作为边加入。

### EPIC-2: Skill 体系重构 — 从 67 个 guard-rule 到 15 个聚焦 Skill

**当前问题**: 67 个 guard-rule 跨 5 语言分散，C/C++ 检测能力不如灵码 30 个 Skill。规则只认裸函数名，排除安全变体，无结构化证据链，无精度控制。

**重构目标**: 借鉴灵码的 Skill 架构，将 67 个 guard-rule 精简为 ~15 个聚焦 C/C++ 的 Skill，每个 Skill 自包含（SKILL.md + references/），支持安全变体参数审计、证据链、5 轮反思。

#### 2.2.2 15 个 Skill 定义（从灵码 30 个精选 + SecGuardian 补充）

| # | Skill | 来源 | 对应 call_sites category | 检测什么 |

|---|-------|------|-------------------------|---------|

| 1 | buffer_overflow | 灵码 memory | string + memory | strcpy/strcat/sprintf 及 `_s` 变体参数误用 |

| 2 | null_dereference | 灵码 memory | memory | malloc/calloc/realloc 后无 NULL 检查 |

| 3 | memory_leak | 灵码 memory | memory | malloc/calloc 无配对 free |

| 4 | double_free | 灵码 memory | memory | 同一指针多次 free |

| 5 | use_after_free | 灵码 memory | memory | free 后继续使用指针 |

| 6 | integer_overflow | 灵码 memory | memory | 整数运算溢出导致缓冲区大小错误 |

| 7 | resource_leak | 灵码 resource | io | fopen/socket/open 无配对 close |

| 8 | command_injection | 灵码 security | exec | system/popen/exec 参数来自用户输入 |

| 9 | input_validation | 灵码 security | exec | 外部输入未校验即使用 |

| 10 | hardcoded_secrets | SecGuardian 补充 | crypto | 密钥/密码硬编码 |

| 11 | must_check | 灵码 contract | memory + io | 函数返回值必须检查但未检查 |

| 12 | ownership_transfer | 灵码 contract | memory | 所有权转移后原指针继续使用 |

| 13 | api_semantic_misuse | 灵码 semantics | * | API 副作用与隐式语义误用 |

| 14 | lock_misuse | 灵码 resource | sync | 互斥锁 lock/unlock 不配对 |

| 15 | error_propagation | 灵码 contract | * | 错误码未传播或被吞没 |

**从 67 → 15 的理由**:

- 67 个规则中大量是跨语言重复（同一规则 5 个语言版本），C/C++ 是主要场景，先聚焦

- 灵码验证了 30 个 Skill 覆盖 C/C++ 主要漏洞类别，15 个是精简版（去掉 overlap 和低频项）

- contract/semantics 类别是灵码的创新，捕获纯内存安全规则遗漏的问题（如 must_check、api_semantic_misuse）

#### 2.2.3 SKILL.md 模板（借鉴灵码，融合索引器信号）

每个 Skill 的 SKILL.md 遵循统一模板：

```markdown

# <Skill Name> 检视算子

## 元数据

- id: memory.buffer_overflow

- severity: critical

- cwe: CWE-120

- category: memory

- signal_source: call_sites[category="string" OR category="memory"]

## 信号预筛

从 index.json 的 call_sites 中筛选：

- callee 匹配: strcpy, strcpy_s, strcat, strcat_s, sprintf, sprintf_s, memcpy, memcpy_s, gets, gets_s, snprintf

- 按信号分组: 非 _s 变体 → 高优先级; _s 变体 → 参数审计优先级

## 检视协议

### Step 1: 信号确认

对每个预筛信号:

1. 读取调用点源码（±15 行）

2. 确认调用点真实存在（排除注释/宏/条件编译）

### Step 2: 证据链构建

构建 Source → Propagate → Sink 证据链:

- Source: 缓冲区目标（dst）的声明和大小

- Propagate: 数据从 src 到 dst 的传递路径

- Sink: 实际写入大小 vs 目标缓冲区大小

### Step 3: 安全变体参数审计（★ 关键新增）

对 _s 变体调用，检查:

- strcpy_s(dst, dsize, src): dsize 是否 == sizeof(dst)? dst 是否为数组（非指针参数）?

- memcpy_s(dst, dsize, src, n): dsize >= n? dsize == sizeof(dst)?

- sprintf_s(buf, size, fmt, ...): size == sizeof(buf)? fmt 含 %s 时 src 是否受控?

- snprintf(buf, size, fmt, ...): 返回值是否被检查?

### Step 4: 跨函数补证

如果 Sink 函数的缓冲区来自调用者:

1. 沿调用图向上追踪 1 层（max depth 1）

2. 确认调用者传入的缓冲区大小

3. 超过 depth 1 → 降级为 "可疑"（不报告为确认漏洞）

### Step 5: 5 轮反思

1. **事实校对**: 证据链中每个断言是否有源码支撑?

2. **因果闭环**: Source 大小 < Sink 写入大小 → 是否必然溢出?

3. **寻找豁免**: 是否有运行时检查、编译期常量、平台保证?

4. **根因归并**: 同一缓冲区的多个 Sink → 合并为 1 个 finding

5. **保守定性**: 证据不完整 → 降级; 证据完整 → 按严重度定级

# 缓冲区溢出规则

## 不安全函数对

| 不安全 | 安全替代 | 溢出条件 |

|--------|---------|---------|

| strcpy(dst, src) | strcpy_s(dst, dsize, src) | strlen(src) >= sizeof(dst) |

| strcat(dst, src) | strcat_s(dst, dsize, src) | strlen(dst)+strlen(src) >= sizeof(dst) |

| sprintf(dst, fmt, ...) | sprintf_s(dst, size, fmt, ...) | 输出长度 >= sizeof(dst) |

| gets(dst) | gets_s(dst, size) | 输入长度 >= sizeof(dst) |

| memcpy(dst, src, n) | memcpy_s(dst, dsize, src, n) | n > sizeof(dst) |

## 安全函数误用（★ 灵码核心洞察）

安全函数 _s 并非自动安全。以下情况仍可溢出:

1. **dsize 不等于 sizeof(dst)**

- strcpy_s(buf, 256, src) 但 buf 只有 128 字节 → 溢出

- strcpy_s(buf, sizeof(buf), src) 但 buf 是指针参数 → sizeof(buf) = 8（指针大小）

2. **dsize 来自不可信源**

- memcpy_s(dst, user_input_len, src, n) → user_input_len 可被篡改

3. **snprintf 返回值未检查**

- snprintf 返回值 > size → 输出被截断，调用者可能误判

4. **memmove 重叠区域**

- memmove(dst, src, n) 当 dst 和 src 重叠 → 未定义行为

```

## 4. 关键设计决策

### 4.1 为什么不把检测完全交给 LLM？

| 方案 | 优势 | 劣势 |

|------|------|------|

| LLM 全权检测 | 灵活，能理解语义 | 不可靠、不可复现、642 × 67 = 43094 组合无法遍历 |

| 确定性引擎 + LLM 判断 | 可靠、可复现 | 引擎需要编程实现 |

| **Dispatcher-Worker + 索引器信号** | 可靠、可复现、高效 | 需要重构索引器 + Skill 体系 |

**决策**: 采用灵码验证有效的 Dispatcher-Worker 模式，加上 SecGuardian 独有的索引器信号聚焦。Worker 仍读实际代码（不是只读索引），但索引器告诉它们去哪找。

### 4.2 为什么保留索引器而不是像灵码一样去掉？

| 方案 | 优势 | 劣势 |

|------|------|------|

| 去掉索引器（灵码方式） | 简单，Worker 全量遍历 | Worker 重复读文件，大仓库效率低 |

| 保留索引器但修复产出 | Worker 精准聚焦，效率高 | 需要重构索引器 |

**决策**: 保留索引器，修复产出。索引器的 `call_sites` 是 Worker 的任务清单——没有它，Worker 要遍历 642 个文件找 `strcpy_s`；有了它，Worker 直接知道第 142 行有 `strcpy_s(dst, sizeof(dst), src)` 需要审计。

### 4.3 为什么 67 个规则精简为 15 个 Skill？

| 方案 | 优势 | 劣势 |

|------|------|------|

| 保留 67 个规则 | 覆盖面广 | 跨语言重复、C/C++ 检测能力弱、LLM 上下文溢出 |

| 精简为 15 个 Skill | 聚焦 C/C++、每个 Skill 自包含、Worker 上下文可控 | 其他语言暂不覆盖 |

**决策**: 先聚焦 C/C++（idm 仓库场景），15 个 Skill 覆盖灵码验证有效的检测类别。其他语言后续按需添加。67 → 15 不是删减，是**合并同类项 + 丢弃不适用的**。

### 4.4 为什么采用 suppress-first 而不是 report-first？

| 方案 | 优势 | 劣势 |

|------|------|------|

| report-first（当前） | 不遗漏 | 误报多，用户信任度低 |

| suppress-first（灵码） | 误报少，用户信任度高 | 可能遗漏 |

**决策**: 采用 suppress-first。理由：当前系统 0 检出，用户已不信任。先建立信任（低误报），再逐步提升召回率。5 轮反思确保抑制决策有据可查。

### 4.5 为什么不引入完整的 CFG/DFG/SSA？

| 方案 | 实现成本 | 检测提升 |

|------|---------|---------|

| 完整 CFG + DFG + SSA | 极高 | 高（精确数据流追踪） |

| 调用点图 + Source-Sink 边 | 中等 | 中等（覆盖 80% 常见漏洞模式） |

| 当前方案（符号表 + 文本匹配） | 低 | 几乎为零 |

**决策**: 先实现调用点图 + Source-Sink 边（性价比最高）。Worker 的跨函数补证协议（max depth 3）弥补精确数据流的缺失。后续视需求迭代到完整 CFG/DFG。

## 5. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |

## 8. 架构验证实验报告：Fact-Anchored Reflection 协议

> 实验日期: 2026-07-08 | 验证方法: 人工模拟 LLM 分析 + 事实锚定反思

### 8.1 实验目的

验证 Fact-Anchored Reflection 协议在各能力域的 5 个代表性 call_site 上的有效性。核心问题：**反思轮是否真的提升了检测质量，还是只是"为了反思而反思"？**

### 8.2 协议定义

**分析阶段** (Step 1-4): Signal confirmation → Evidence chain → Parameter audit → Cross-function corroboration → 产出初始 verdict

**反思阶段** (3 个事实锚定问题 + 判定矩阵):

对每个能力域定义专用 Q1-Q2-Q3：

| 能力域 | Q1 | Q2 | Q3 |
|--------|----|----|----|
| memory (buffer_overflow) | 目标缓冲区大小 ≥ 拷贝大小? | 拷贝大小是编译期常量? | 源数据至少有 n 字节? |
| sync (lock_misuse) | 所有退出路径都有 unlock? | 是否存在 unlock 调用? | 子函数能释放此锁? |
| crypto | 算法已知弱? | 密钥已正确初始化? | 密钥长度足够? |
| io (path_traversal) | 路径含用户控制输入? | 路径已 sanitized? | I/O 调用安全? |
| exec (command_injection) | 参数来自外部源? | sink前有校验? | 纯字符串字面量? |

**判定矩阵规则**: 三个事实锚定覆盖 → 无需反思; 两个覆盖且一致 → 单一反思确认; 单一覆盖或矛盾 → 强制完整反思

### 8.3 Test A: alloc_user_buffer strcpy(buf, "initialized") — suppress

| 阶段 | 输出 |
|------|------|
| **信号** | caller=alloc_user_buffer callee=strcpy line=107 args=["buf","\"initialized\""] category=string |
| **源码** | buf=malloc(user_size); memset(buf,0,user_size); strcpy(buf,"initialized") |
| **初始分析 verdict** | strcpy 写入动态 buffer, dst 大小取决于 user_size(参数可控), **可能溢出** → **suspicious** |
| **反思 Q1** | 目标缓冲区大小 ≥ 拷贝大小? buf=malloc(user_size), 但 src="initialized" 固定12字节(含null)。只要 user_size ≥ 12 就安全。Q1 = **YES**(条件满足) |
| **反思 Q2** | 拷贝大小是编译期常量? "initialized" 是字面量, 12字节固定。Q2 = **YES** |
| **反思 Q3** | 源数据至少有 n 字节? "initialized" 字符串常量, 编译期已知12字节。Q3 = **YES** |
| **判定矩阵** | Q1=YES, Q2=YES, Q3=YES → **SUPPRESS** (三绿灯) |
| **Δ 分析** | ❗**反思防止了误报**。纯分析被"strcpy + 动态 buffer"吓到, 标注为可疑。反思通过 3 个事实问题确认这是一次安全的固定常量拷贝 → 正确抑制 |

### 8.4 Test B: concurrency.c main pthread_mutex_lock — missing unlock

| 阶段 | 输出 |
|------|------|
| **信号** | caller=main callee=pthread_mutex_lock line=130 category=sync |
| **源码** | pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER; lock(&m); //work... return 0; //No unlock! |
| **初始分析 verdict** | 130行 lock, 133行 return, 中间无 unlock → **CONFIRMED** (CWE-667) |
| **反思 Q1** | 所有退出路径都有 unlock? 仅一条路径(return 0), 无 unlock。Q1 = **NO** |
| **反思 Q2** | 是否存在 unlock 调用? main 函数内没有 pthread_mutex_unlock。Q2 = **NO** |
| **反思 Q3** | 子函数能释放此锁? &m 是局部变量, 未传给任何 callee。Q3 = **NO** |
| **判定矩阵** | Q1=NO, Q2=NO, Q3=NO → **CONFIRMED** (三红灯) |
| **Δ 分析** | 反思正确确认, 未改变 verdict。三独立事实问题交叉验证了同一结论, 置信度更高 |

### 8.5 Test C: crypto.c DES_set_key_unchecked — weak crypto

| 阶段 | 输出 |
|------|------|
| **信号** | caller=encrypt_data_weak callee=DES_set_key_unchecked line=58 category=crypto |
| **源码** | DES_cblock key; //UNINITIALIZED! DES_set_key_unchecked(&key, &schedule); DES_ecb_encrypt(...) |
| **初始分析 verdict** | DES 是弱算法(56-bit, 24小时内可暴力破解), 使用 EC模式泄露模式 → **CONFIRMED** |
| **反思 Q1** | 算法已知弱? DES 被 NIST 废止, 56-bit 有效密钥。Q1 = **YES** |
| **反思 Q2** | 密钥已正确初始化? DES_cblock key 是栈上未初始化变量 = 垃圾数据作为密钥。Q2 = **NO** ❌ |
| **反思 Q3** | 密钥长度足够? DES_cblock = 8字节(64-bit, 56有效)。Q3 = **NO** (56-bit << 128+ 推荐值) |
| **判定矩阵** | Q1=YES, Q2=NO, Q3=NO → **CONFIRMED, 且发现额外问题** |
| **⛔ 关键 Δ** | ❗**反思发现了纯分析遗漏的 CRITICAL 问题: 密钥未初始化!** 纯分析只说"DES is weak", 反思 Q2 发现密钥是栈垃圾 → 所有"加密"数据可被读取栈内存者解密。这是**完全不同的漏洞类别**(信息泄露), 且严重度比弱算法更高。→ **暴露了 Q schema 的间隙: 没有针对"密钥来源"的专用问题** |

### 8.6 Test D: system.c fopen(path, "r") — path traversal

| 阶段 | 输出 |
|------|------|
| **信号** | caller=read_user_file callee=fopen line=43 args=["path","\"r\""] category=io |
| **源码** | snprintf(path, 512, "/var/data/%s", filename); fopen(path, "r"); //filename无校验 |
| **初始分析 verdict** | filename 拼接在路径中, 无 ../ 检查 → **CONFIRMED** (CWE-22) |
| **反思 Q1** | 路径含用户控制输入? filename 直接参数传入, 无校验。Q1 = **YES** |
| **反思 Q2** | 路径已 sanitized? 无 realpath(), 无 basename(), 无 ../ 过滤。Q2 = **NO** |
| **反思 Q3** | I/O 调用安全? fopen 会跟随符号链接。Q3 = **NO** |
| **判定矩阵** | Q1=YES, Q2=NO → **CONFIRMED** |
| **Δ 分析** | 反思不改变 verdict, 但更精确: 分析说"可能路径遍历", 反思指出"Q1=YES 参数可变, Q2=NO 零校验 → 明确漏洞路径"。这为修复提供了精确位置(在 line42-43 间插入校验) |

### 8.7 Test E: network.c memcpy — 复杂多调用场景 (核心测试)

| 方面 | 输出 |
|------|------|
| **信号 1** (line 53) | caller=parse_packet callee=memcpy args=["&packet->header","header","sizeof(PacketHeader)"] |
| **信号 2** (line 60) | caller=parse_packet callee=memcpy args=["packet->data","raw_data+HEADER_SIZE","header->data_size"] |
| **请注意**: indexer 产出了 **2 个** call_site, 不是 1 个。Dispatcher 需要将两个信号都传给 Worker。 |

#### 信号 1 (line 53)

| 阶段 | 输出 |
|------|------|
| **初始分析** | memcpy 16字节固定长度 into PacketHeader 结构体(also 16字节) → **Safe** |
| **反思 Q1** | dst buffer大小 ≥ 拷贝大小? sizeof(PacketHeader)=16, n=sizeof(PacketHeader)=16 → 相等。Q1 = **YES** |
| **反思 Q2** | 拷贝大小是编译期常量? sizeof(PacketHeader) 编译期确定。Q2 = **YES** |
| **反思 Q3** | 源数据至少有 n 字节? line 36 守卫: raw_size < sizeof(PacketHeader) → return -1。Q3 = **YES** |
| **判定矩阵** | Q1=YES, Q2=YES, Q3=YES → **SUPPRESS** |

#### 信号 2 (line 60)

| 阶段 | 输出 |
|------|------|
| **初始分析** | header->data_size 来自网络包, 且 size check 存在整数溢出绕过(line 46)。packet->data = malloc(header->data_size), 无 NULL 检查。→ **CONFIRMED** |
| **反思 Q1** | dst buffer大小 ≥ 拷贝大小? malloc(header->data_size) = header->data_size, 拷贝也是 header->data_size → 理论相等。但 line 46 的整数溢出绕过使 data_size 可通过 CHECK 但实际远超源数据。Q1 = **YES** (size匹配但前提被攻破) |
| **反思 Q2** | 拷贝大小是编译期常量? header->data_size 来自网络 → 运行时值。Q2 = **NO** |
| **反思 Q3** | 源数据至少有 n 字节? 通过整数溢出绕过, data_size=0xFFFFFFF1 但 raw_data 仅16字节。Q3 = **NO** |
| **判定矩阵** | Q1=YES(有条件), Q2=NO, Q3=NO → **CONFIRMED** |

### 8.7.1 Test E 核心教训

| 发现 | 影响 |
|------|------|
| **信号驱动正确捕获了所有调用点** | indexer 产出 line 53 + line 60 两个 memcpy 信号, 没有被遗漏 |
| **Worker 能正确区分安全 vs 危险调用** | 信号1抑制, 信号2确认 |
| **整数溢出绕过是独立的检测维度** | integer_overflow skill 需要自己的 Worker。buffer_overflow Worker 依赖其假设(如果 size_check 被绕过, buffer_overflow 的 Q2 假设失效) |
| **多信号协作是必须的** | 单个信号分析会遗漏上下文。多个信号 → 同一函数 → Worker 需要看全局 |

### 8.8 跨测试分析

#### 8.8.1 反思 Δ 统计

| 测试 | 纯分析 verdict | 反思后 verdict | Δ 类型 |
|------|---------------|---------------|--------|
| A: strcpy(literal) | **suspicious** (误报风险) | **SUPPRESS** ✅ | **阻止了误报** |
| B: mutex missing unlock | **CONFIRMED** ✅ | **CONFIRMED** | 置信度提升, 未改变 |
| C: DES weak crypto | **CONFIRMED** ✅ | **CONFIRMED + 额外发现** | **发现遗漏的 CRITICAL 问题**(密钥未初始化) |
| D: path traversal | **CONFIRMED** ✅ | **CONFIRMED** | 修复定位更精确 |
| E: memcpy (safe) | **Safe** ✅ | **SUPPRESS** | 结构正确 |
| E: memcpy (危险) | **CONFIRMED** ✅ | **CONFIRMED** | 结构正确 |

#### 8.8.2 Δ 分析结论: 反思轮确实有效

1. **防止误报 (Test A)**: 纯分析看到"strcpy + 动态 buffer"就倾向于标记为可疑。反思通过 Q1-Q2 确认源是固定常量 → 正确抑制。没有反思就会产出一个误报。

2. **发现遗漏 (Test C)**: 纯分析聚焦于"DES 是弱算法"这个明显结论, 完全忽略了"密钥未初始化"这个更大的问题。反思 Q2 直接问"密钥正确初始化了?" → 发现漏洞。**反思迫使 LLM 检查它本该检查但忘了检查的问题。**

3. **确证结论 (Test B/D/E safe variant)**: 反思不改变正确结论, 但增加了事实锚定验证。对分析已准确的 case, 反思不会引入错误反转。

#### 8.8.3 发现的设计缺陷

| 缺陷 | 影响 | 修复 |
|------|------|------|
| **Q schema 必须域专用** (Test C) | 通用 Q1-Q2-Q3 无法覆盖密钥初始化问题 | 每个 skill domain 定义专用 Q set |
| **整数溢出依赖 (Test E)** | buffer_overflow 的 Q1 假设 size_check 有效, 但 integer_overflow 可能绕过它 | buffer_overflow 先检查 integer_overflow 覆盖情况 |
| **无"跨信号合成"阶段** (Test E) | Worker 逐个分析信号, 但 line 53 和 line 60 的 memcpy 只能合成分析 | Worker 协议增加"同函数信号归并分析"步骤 |

### 8.9 协议设计迭代建议

基于实验证据, 证伪旧设计(5 轮反思), 提出新设计:

**旧: 5 轮反思** → 同 LLM 同上下文同框架 → 5 轮产出同质化结论(已被证实无效)

**新: 3 阶段分析协议**:

```
Step 1-4: 标准分析(同灵码)
  → 初始 verdict + 证据链

Step 5a: 事实锚定反思
  → 每个 skill 域有 3 个专用 Yes/No 事实问题
  → 判定矩阵: 三绿灯→抑制; 两灯以上安全→可控; 两红灯以上→确认; 混合→强制详细分析
  
Step 5b: 正交验证(可选)
  → 如果极重要或信号量大: 从不同 skill 问不同的问题(多功能验证)
  → 例如: buffer_overflow + integer_overflow 交叉验证 Test E 的场景
```

**成本**:
- Step 1-4 + Step 5a: ~1 轮 LLM 调用, 比 5 轮反思节省 80% token
- Step 5b 仅用于高价值场景
