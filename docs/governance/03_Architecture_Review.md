# 03 — 架构安全评审 (Architecture Security Review)

> **对应 Sheet:** `03_Architecture_Review`  
> **牵引方向:** SecGuardian 架构安全评审能力——在应用上线前识别设计缺陷，提供架构层面的安全评估。

---

## 1. 概述

架构安全评审关注**设计阶段的安全风险**，而非实现阶段的代码漏洞。本 sheet 涵盖 **5 大架构安全分类**，每类 16 条要求，共计 **80 条架构评审控制项**。

---

## 2. 分类体系

| 分类 | 控制目标 | 严重度分布 |
|---|---|---|
| **Trust Boundary** (信任边界) | 识别并加固系统间的信任边界，防止跨边界未授权访问 | 6×Medium, 6×High, 4×Critical |
| **Threat Model** (威胁建模) | 系统化识别威胁、评估风险、制定缓解措施 | 6×Medium, 6×High, 4×Critical |
| **Data Flow** (数据流) | 保障数据在传输、存储、处理过程中的机密性和完整性 | 6×Medium, 6×High, 4×Critical |
| **Identity** (身份管理) | 身份认证与授权体系架构设计 | 6×Medium, 6×High, 4×Critical |
| **Resilience** (韧性/容错) | 架构层面的故障隔离、降级与恢复能力 | 6×Medium, 6×High, 4×Critical |

---

## 3. 分类详解与最佳实践

### 3.1 信任边界 (Trust Boundary)

**定义：** 系统内部不同信任级别区域之间的分界线。跨越信任边界的数据必须经过安全校验。

**常见信任边界：**
- 外部网络 → DMZ
- DMZ → 内部网络
- 用户输入层 → 业务逻辑层
- 多租户系统 → 租户间隔离

**检测清单：**

| 检查项 | 说明 | 严重度 |
|---|---|---|
| 所有跨边界数据是否经过验证 | 输入验证不可绕过 | High |
| 边界处是否实施最小权限 | 每个边界组件只有所需最小权限 | Medium |
| 内部协议是否可被外部访问 | 内部 RPC/gRPC 应不可从外部直接调用 | Critical |
| DMZ 是否隔离 | Web 服务器不应直接访问数据库 | High |
| 边界协议是否安全 | HTTP → HTTPS 重定向，不支持明文 | Critical |

### 3.2 威胁建模 (Threat Model)

**方法论 — STRIDE (Microsoft)：**

| 威胁 | 定义 | 缓解措施 |
|---|---|---|
| Spoofing (冒充) | 冒充用户或系统身份 | 强认证 + MFA |
| Tampering (篡改) | 修改数据或代码 | 签名 + 完整性校验 |
| Repudiation (抵赖) | 否认已进行的操作 | 审计日志 + 数字签名 |
| Information Disclosure (信息泄露) | 数据被未授权读取 | 加密 + 访问控制 |
| Denial of Service (拒绝服务) | 系统不可用 | 限流 + 弹性伸缩 |
| Elevation of Privilege (提权) | 获取更高权限 | RBAC + 最小权限 |

**架构评审中的威胁建模流程：**

1. **绘制数据流图 (DFD)** — 识别数据在组件间的流动
2. **识别威胁** — 对每个 DFD 元素应用 STRIDE
3. **评估风险** — DREAD / CVSS 打分
4. **制定缓解措施** — 架构变更或控制措施
5. **验证** — 确保缓解措施有效

### 3.3 数据流 (Data Flow)

**核心要求 — 数据在所有状态下的保护：**

| 数据状态 | 要求 | 业界实践 |
|---|---|---|
| **传输中 (In Transit)** | 所有外部链路 TLS 1.2+ | mTLS 用于服务间通信 |
| **存储中 (At Rest)** | 敏感数据字段级加密 | AES-256-GCM / AWS KMS |
| **处理中 (In Use)** | 内存数据保护 | 敏感数据用后即擦除、加密内存 |

**数据流检测清单：**

| 检查项 | 说明 |
|---|---|
| 敏感数据是否流向正确的目的地 | PII 不应进入日志系统 |
| 是否存在数据泄露路径 | 如数据未经加密就持久化 |
| 数据传输路径是否有中间跳 | 中间跳是否增加额外风险 |
| 数据保留期限是否合理 | 过期数据是否自动清除 |
| 数据脱敏是否在边界层完成 | 生产数据进入非生产环境前脱敏 |

### 3.4 身份管理 (Identity)

**对标 — OWASP ASVS V2 (Authentication) + V4 (Access Control)：**

| 架构决策 | 推荐方案 | 不推荐 |
|---|---|---|
| 认证协议 | OAuth 2.0 + OIDC | 自建密码认证 |
| 会话管理 | JWT (短期) + Refresh Token | 长期固定 Session |
| MFA 策略 | 基于风险的自适应 MFA | 静态全部 MFA |
| 服务间认证 | mTLS | 共享 API Key |
| 密钥轮转 | 自动轮转 (≤90 天) | 手动轮转或不轮转 |

### 3.5 韧性/容错 (Resilience)

**架构层面保障：**

| 模式 | 说明 | 架构检查点 |
|---|---|---|
| 断路器 (Circuit Breaker) | 防止级联故障 | 外部依赖是否配置断路器 |
| 舱壁隔离 (Bulkhead) | 隔离故障域 | 限流器是否按用户/租户隔离 |
| 优雅降级 (Graceful Degradation) | 核心功能可用 | 非关键依赖失效时是否优雅处理 |
| 重试策略 | 不可用时的自动恢复 | 重试是否伴随退避和 jitter |
| 限流和熔断 | 避免资源耗尽 | API 网关是否配置速率限制 |

## 4. 业界最佳实践对标

### 4.1 C4 模型 + 安全视角

[C4 模型](https://c4model.com/) 从 4 个层次描述架构，每个层次应嵌入安全视角：

| 层次 | 安全评审关注点 |
|---|---|
| Context (上下文) | 威胁主体、外部依赖、信任边界 |
| Container (容器) | 服务间认证、数据流加密、技术选型安全 |
| Component (组件) | 组件间接口安全、权限模型 |
| Code (代码) | 具体实现的安全编码检查 (由 SAST 覆盖) |

### 4.2 SAMM (软件保障成熟度模型)

[OWASP SAMM](https://owaspsamm.org/model/) 的安全架构实践 (SA)：

| 成熟度 | 目标 |
|---|---|
| **SA 1** | 识别关键应用组件并评估安全影响 |
| **SA 2** | 对所有应用进行安全架构评审 |
| **SA 3** | 安全架构融入整个开发流程并量化度量 |

**SecGuardian 目标：SA 2 → SA 3**

## 5. SecGuardian 牵引方向

### 5.1 架构评审自动化

当前 SecGuardian 三个 skill 聚焦于代码级检测，**架构评审能力缺失**。未来应：

1. **架构描述输入** — 支持 DFD / C4 模型描述作为扫描输入
2. **自动威胁识别** — 根据架构描述自动识别 STRIDE 威胁
3. **架构规则库** — 预置 80+ 架构级检查规则
4. **评审报告生成** — 结构化的架构安全评审报告

### 5.2 增量发展路径

| 阶段 | 能力 | 产出 |
|---|---|---|
| **Phase 1** | 架构描述 YAML/JSON 解析器 | 支持输入架构配置 |
| **Phase 2** | 规则引擎 (信任边界 + 数据流) | 静态架构分析 |
| **Phase 3** | 集成威胁建模建议 | 威胁自动识别 + 缓解建议 |
| **Phase 4** | CI/CD 集成 | PR 级架构评审门禁 |

### 5.3 与现有能力整合

```
现有 SecGuardian (代码级)
   │
   ├── secguard   → 安全基线扫描 (编码/配置)
   ├── secreview  → 安全审查 (代码+架构)
   └── secaudit   → 安全审计 (合规证据)
         │
         ▼
  新增: 架构评审模块
  接受: DFD / C4 YAML / 云资源清单
  输出: STRIDE 威胁表 + 信任边界图 + 缓解建议
```
